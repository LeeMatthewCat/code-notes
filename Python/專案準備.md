# 概念與原理

## Industry Standard 行業標準專案

開發專案時，將程式碼、測試、設定檔與文檔**結構化與模組化**的規範體系。

### 什麼是「單檔劇本 (Single-file Script)」？

初學者剛開始學習 Python 時，通常會在編輯器裡新建一個 `main.py` 或 `demo.py`。
開發者會把所有的變數、函式、爬蟲邏輯、資料庫連線甚至測試碼全部擠在這幾百行的單一檔案裡。
這種缺乏架構劃分的程式碼形式就稱為「單檔劇本」。

### 為什麼現代工程必須告別單檔劇本？

當專案從小玩具成長為真正的軟體產品時，單檔劇本會帶來致命的缺陷：

- **維護成本極高**：在數千行的單一檔案中修改邏輯，容易牽一髮而動全身。
- **無法多人協同**：多位工程師同時修改 `main.py` 時，提交 Git 會產生大量版本衝突 (Merge Conflict)。
- **無法模組化複用**：外部專案無法透過 `import` 引用特定函式，只能手動複製貼上。
- **無法自動化測試**：業務邏輯與執行入口混雜，無法針對單一功能編寫獨立單元測試 (Unit Test)。

> **[生動比喻]**：  
> 單檔劇本就像雜亂的玩具收納箱，剪刀、筆刷與零件全部塞在同一個格子裡。要找任何工具都必須把整個箱子倒出來。  
> 行業標準專案就像現代化汽車工廠，引擎、輪胎與電路車間各自獨立，最後在裝配線上透過標準介面組合。

## Src Layout 原始碼隔離架構

將專案真正要執行的 Python 原始碼統一收納在 `src/` 資料夾內部的工程設計模式。

### 什麼是 Src Layout？

Python 社群歷史上有兩種主流目錄架構：

1. **Flat Layout (扁平結構)**：直接把專案套件資料夾（例如 `my_project/`）放在專案最頂層的根目錄。
2. **Src Layout (源碼隔離結構)**：在根目錄下建立 `src/` 資料夾，並把 `my_project/` 封裝在 `src/` 內部。

現代 Python 官方打包指南 (PyPA) 與主流建置工具（如 `uv`、`hatch`、`setuptools`）一致推薦使用 **Src Layout**。

### 為什麼要多加一層 `src/`？（解決測試偽陽性陷阱）

當開發者在終端機執行 `pytest` 或執行 Python 程式時，Python 的模組搜尋路徑 (`sys.path`) 預設會**將當前的工作目錄 (Current Working Directory) 自動加入搜尋清單首位**。

- **Flat Layout 的隱藏災難**：  
  根目錄下直接存在 `my_project/` 資料夾。執行 `pytest` 時，直譯器會直接匯入根目錄下**未經打包、未經安裝的原始碼**。  
  這會引發「測試偽陽性 (Import Paranoia)」：測試全部通過，但使用者透過 `pip install` 安裝套件時，卻因為遺漏非 `.py` 靜態檔案或設定檔而直接崩潰。
- **Src Layout 的防禦機制**：  
  根目錄下沒有 `my_project/` 資料夾，原始碼被隔離在 `src/` 內部。如果在根目錄直接執行測試，直譯器會拋出找不到模組的錯誤。  
  這迫使開發者必須先將套件以**可編輯模式 (Editable Mode)** 安裝至[[終端指令#虛擬環境|虛擬環境]]中。此舉確保開發測試環境與最終使用者安裝環境完全一致。

> **[生動比喻]**：  
> `src/` 就像工廠的保密生產車間，根目錄則是對外開放的展示門市。  
> 若沒有 `src/` 隔離，測試人員就會直接拿生產線上塗料未乾的半成品進行檢驗；有了 `src/`，產品必須通過標準包裝與出廠檢驗，才能進行驗證與交付。

# 專案環境建置與標準起手式流程

從零啟動一個現代 Python 專案時，環境建置與依賴管理是決定後續工程穩定度的核心基石。

## 專案環境初始化標準流程

標準建置流程包含目錄初始化、環境隔離、結構生成與依賴安裝六大環節。

### Step 1：建立專案目錄與 Git 初始化

在終端機建立專案專屬根目錄，並立刻啟動版本控制：

```shell
# 1. 建立專案目錄並進入
mkdir my_project
cd my_project

# 2. 初始化 Git 倉庫
git init
```

---

### Step 2：建立與管理虛擬環境

#### uv 虛擬環境建立與管理

現代 Python 開發強烈建議使用 `uv` 取代傳統的 `python -m venv` 與 `pip`。

- **極速效能**：`uv` 採用 Rust 開發，建立虛擬環境與解析依賴速度提升 10 至 100 倍。
- **免升級困擾**：傳統 `venv` 內建的 `pip` 經常過舊，需要額外升級；`uv` 則具備現代化自給自足的套件管理核心。
- **版本無縫切換**：可直接透過參數指定特定 Python 版本建立環境，無需手動配置複雜路徑。

```shell
# 1. 使用當前系統 Python 建立 .venv 虛擬環境
uv venv

# 2. 或指定特定 Python 版本建立環境 (例如 Python 3.12)
uv venv --python 3.12

# 3. 手動啟動虛擬環境 (macOS / Linux)
source .venv/bin/activate

# 4. 退出虛擬環境
deactivate
```

> **[小提醒]**：  
> 在 `uv` 工作流中，日常開發**完全不需要手動執行 `source .venv/bin/activate`**。  
> 透過 `uv run` 指令，工具會自動辨識當前目錄下的 `.venv` 並在其中執行指令。

---

### Step 3：一鍵生成標準目錄與空白檔案

在專案根目錄下，透過 Shell 命令一鍵建立符合 Src Layout 的標準結構：

```shell
# 1. 建立 src 核心目錄、測試目錄、文件目錄與維運目錄
mkdir -p src/my_project/core tests/unit tests/integration docs scripts

# 2. 建立 package 標記檔案與進入點
touch src/my_project/__init__.py
touch src/my_project/__main__.py
touch src/my_project/py.typed
touch src/my_project/core/__init__.py

# 3. 建立測試環境設定檔
touch tests/__init__.py
touch tests/conftest.py
```

---

### Step 4：配置版本控制黑名單與環境變數範本

在進行任何代碼編寫前，必須先配置 `.gitignore` 與 `.env.example`，防止敏感資訊外洩。

```shell
# 1. 建立 .gitignore 檔案
cat << EOF > .gitignore
# Python 快取
__pycache__/
*.py[cod]
*$py.class

# 虛擬環境
.venv/
venv/
ENV/

# 敏感環境變數
.env
.env.local

# 測試與覆蓋率報告
.pytest_cache/
.coverage
htmlcov/
.mypy_cache/
.ruff_cache/

# 作業系統垃圾檔案
.DS_Store
Thumbs.db
EOF

# 2. 建立公開環境變數範本
cat << EOF > .env.example
APP_ENV=development
DEBUG=True
PORT=8000
API_KEY=your_secret_api_key_here
DATABASE_URL=sqlite:///./dev.db
EOF

# 3. 複製出本機實際使用的私密環境變數檔
cp .env.example .env
```

---

### Step 5：撰寫 pyproject.toml 專案配置

在專案根目錄建立 `pyproject.toml`，集中定義專案元數據、建置系統與開發工具：

```toml
[build-system]
requires = ["setuptools>=61.0"]
build-backend = "setuptools.build_meta"

[project]
name = "my_project"
version = "0.1.0"
description = "符合現代行業標準的完整 Python 專案"
readme = "README.md"
requires-python = ">=3.10"
license = { text = "MIT" }
authors = [
    { name = "Matthew", email = "matthew@example.com" }
]
dependencies = [
    "python-dotenv>=1.0.0",
]

[project.optional-dependencies]
dev = [
    "pytest>=8.0.0",
    "pytest-cov>=4.1.0",
    "mypy>=1.8.0",
    "ruff>=0.2.0",
]

[project.scripts]
my-cli = "my_project.__main__:main"

[tool.pytest.ini_options]
minversion = "8.0"
addopts = "-ra -q"
testpaths = ["tests"]
pythonpath = ["src"]

[tool.ruff]
line-length = 88
target-version = "py310"

[tool.mypy]
python_version = "3.10"
strict = true
```

---

### Step 6：uv 依賴管理與執行工作流

#### uv 依賴管理與執行工作流

使用 `uv` 進行套件管理時，所有的依賴變更都會自動同步至專案設定檔：

```shell
# 1. 新增正式生產環境依賴 (自動寫入 pyproject.toml 的 dependencies)
uv add python-dotenv requests

# 2. 新增開發與測試專用依賴 (自動寫入 optional-dependencies.dev)
uv add --dev pytest pytest-cov ruff mypy

# 3. 移除指定依賴
uv remove requests

# 4. 鎖定全專案依賴版本樹 (生成 uv.lock)
uv lock

# 5. 依據鎖定檔同步還原環境 (適合團隊協同或 CI 環境)
uv sync

# 6. 以可編輯模式 (Editable Mode) 安裝當前套件與開發依賴
uv pip install -e ".[dev]"
```

---

### Step 7：免啟動環境執行與自動化驗證

藉由 `uv run`，命令列可以在不手動啟動虛擬環境的前提下，直接調用環境內的二進位執行檔或模組：

```shell
# 1. 執行專案自訂 CLI 指令
uv run my-cli

# 2. 透過模組路徑啟動主程式
uv run python -m my_project

# 3. 執行自動化測試
uv run pytest

# 4. 執行代碼靜態檢查與格式化
uv run ruff check
uv run ruff format

# 5. 執行嚴格型別檢查
uv run mypy src
```

# 現代 Python 專案目錄結構全貌

以下為一個符合現代 Python 最高行業標準（Src Layout）的完整專案結構樹狀視圖：

```text
my_awesome_project/            # [專案根目錄] 專案的最頂層資料夾
├── .git/                      # Git 版本控制內部追蹤目錄 (自動生成，不可手動修改)
├── .github/                   # GitHub 平台專用目錄
│   └── workflows/             # CI/CD 自動化工作流程定義檔 (Actions 腳本)
│       └── ci.yml
├── docs/                      # [專案說明文件目錄] 存放技術文件與架構指南
│   ├── index.md
│   └── setup_guide.md
├── scripts/                   # [維運腳本目錄] 獨立運行的輔助小工具與維護腳本
│   └── init_db.py
├── src/                       # [原始碼隔離層] 防止測試偽陽性的核心保護罩
│   └── my_awesome_project/    # [Package 本體] 真正要被打包與發布的 Python 包 (蛇形命名)
│       ├── __init__.py        # 包入口：定義對外暴露的 API 與版本號 (__version__)
│       ├── __main__.py        # CLI 執行入口：支援 python -m my_awesome_project 啟動
│       ├── py.typed           # PEP 561 標記：告知第三方工具本套件支援型別註記
│       ├── config.py          # 設定檔載入器：讀取 .env 或系統環境變數
│       ├── exceptions.py      # 自訂異常類別：定義專案專屬的 Exception 體系
│       ├── core/              # 核心業務邏輯子包
│       │   ├── __init__.py
│       │   └── engine.py
│       ├── services/          # 外部服務整合子包 (API 客戶端、資料庫連線)
│       │   ├── __init__.py
│       │   └── api_client.py
│       └── utils/             # 通用小工具子包 (輔助函式、日誌處理)
│           ├── __init__.py
│           └── helpers.py
├── tests/                     # [自動化測試目錄] 存放所有 pytest 測試檔案
│   ├── __init__.py
│   ├── conftest.py            # pytest 共用 Fixture 與測試環境全域設定
│   ├── unit/                  # 單元測試 (Unit Tests)
│   │   └── test_engine.py
```

# 核心目錄職責解析

## src/ 原始碼隔離目錄

### 名字由來
`src` 是英文 **Source (來源 / 原始碼)** 的標準縮寫。在 C++、Rust、Go 等現代程式語言中，`src/` 皆為存放原始碼的標準目錄。

### 核心職責與定位
`src/` 是專案原始碼的**防護箱與隔離外殼**。它的核心目的在於將「產品運行程式碼」與「根目錄下的各種設定檔、測試檔、自動化腳本」進行物理空間的徹底切分。

### 裡面該放什麼資料？
- 專案最終要打包發布或運行的 Python Package（例如 `src/my_awesome_project/`）。

### 絕對不能放什麼資料？
- `[錯誤]` 存放測試檔案（測試檔應嚴格歸入 `tests/`）。
- `[錯誤]` 存放秘密金鑰或 `.env` 檔案。
- `[錯誤]` 存放運作過程產生的日誌、資料集或暫存快取。

> **[生動比喻]**：  
> `src/` 是金庫的防彈玻璃外罩，確保只有經過審查的產品程式碼能留存其中，外部雜物一概無法進入。

## src/專案名稱/ Package 本體

### 命名規範
目錄名稱即為專案套件名稱，**必須嚴格使用蛇形命名 (`snake_case`)**。例如 `my_awesome_project`，嚴禁使用減號 `-` 或空格，否則 Python 直譯器無法透過 `import` 載入。

### 核心職責與內部結構劃分
這是專案業務邏輯的大本營。當使用者透過套件管理工具安裝此專案時，安裝到環境中的即為此目錄內的程式碼。

標準內部子模組劃分職責如下：
- `__init__.py`：套件門面與版本宣告。
- `__main__.py`：CLI 命令列執行入口。
- `config.py`：讀取並驗證環境變數。
- `exceptions.py`：定義專案內部的自訂錯誤型態。
- `core/`：存放專案最核心、最純粹的演算法與業務邏輯。
- `services/`：存放與外部系統互動的程式碼（如 API 呼叫、資料庫連線、快取操作）。
- `utils/`：存放通用的輔助函式（如時間轉換、字串格式化）。

> **[生動比喻]**：  
> 這是汽車的引擎總成，內部汽缸、火星塞與傳動軸各有專屬位置，分工明確。

## tests/ 自動化測試目錄

### 命名規範與 pytest 自動搜尋
目錄名稱固定為 `tests`。現代 Python 測試框架（如 `pytest`）預設會自動掃描名為 `tests` 的目錄。

測試檔案名稱**必須以 `test_` 開頭**（例如 `test_engine.py`），`pytest` 才能自動辨識並執行。

### 核心職責與結構規劃
`tests/` 是專案的品質檢驗站與安全防護網。所有用於驗證程式碼正確性、防止回歸缺陷的自動化測試腳本均存放於此。

- `conftest.py`：存放 `pytest` 全域共用的測試假資料與環境 Fixtures。
- `unit/`：針對單一函式或類別進行的微型快速單元測試。
- `integration/`：驗證多個模組串接、資料庫連線或 API 調用的整合測試。

### 絕對不能放什麼資料？
- `[錯誤]` 存放產品線的實際業務邏輯。
- `[錯誤]` 存放真實的生產環境機密金鑰。

> **[生動比喻]**：  
> `tests/` 是車輛出廠前的碰撞測試實驗室，所有零件都必須在此經過嚴格檢驗，合格後才能上路。

# 必備核心檔案規範與配置範本

## pyproject.toml 專案中央指揮總部

### 檔案職責與 PEP 518/621 規範
`pyproject.toml` 是現代 Python 專案最重要的核心設定檔。它將過去分散在 `setup.py`、`setup.cfg`、`requirements.txt`、`pytest.ini` 等各處的設定集中統整於單一檔案。

### 核心區塊解析
1. **`[build-system]` (建置系統)**：宣告打包專案時使用的後端工具（如 `setuptools` 或 `hatchling`）。
2. **`[project]` (專案元數據與依賴)**：記錄專案名稱、版本、作者，以及專案運行所需的第三方套件清單 (`dependencies`)。
3. **`[project.optional-dependencies]` (可選依賴群組)**：宣告開發、測試或文件生成專用的附加套件。
4. **`[tool.xxx]` (開發工具全域配置)**：集中管理各類輔助工具（如 `pytest`、`ruff`、`mypy`）的執行參數。

> **[生動比喻]**：  
> `pyproject.toml` 是專案的中央指揮總部與數位身分證，所有關於專案身分、零件需求與工作準則的指令皆在此集中發布。

## __init__.py 套件入口與門面匯出

### 檔案職責與身分標記
1. **標記身分**：告知 Python 直譯器該資料夾為一個可被匯入的 **Package (包)**。
2. **控制門面匯出**：當外部調用 `import my_project` 時，執行的即為該目錄下的 `__init__.py`。可透過 `__all__` 清單精準控制公開的函式與類別。

---

### __init__.py 載入生命週期與執行順序

直譯器載入 Package 時固定遵循四大階段：

```text
外部調用: import my_package
   │
   ▼
1. 搜尋定位: Python 在 sys.path 中尋找 my_package/ 目錄
   │
   ▼
2. 頂層執行: 直譯器由上至下完整執行 my_package/__init__.py
   │
   ▼
3. 觸發內部匯入: 執行 __init__.py 內的相對匯入，依序載入子模組
   │
   ▼
4. 註冊快取: 將初始化完成的模組物件存入 sys.modules 快取
```

---

### __init__.py 內部程式碼標準排列順序 (PEP 8 規範)

一個結構嚴謹的 `__init__.py` 應嚴格遵循由上至下的 8 大標準區塊：

```python
# 區塊 1: 模組文件字串 (Package Docstring)
"""
My Project Core Package
~~~~~~~~~~~~~~~~~~~~~~~
提供核心運算引擎與輔助工具介面。
"""

# 區塊 2: 語言特性開關 (__future__ Imports)
from __future__ import annotations

# 區塊 3: Python 原生標準庫匯入 (Standard Library Imports)
import logging
import sys
from typing import Final

# 區塊 4: 第三方套件匯入 (Third-Party Imports)
import pydantic

# 區塊 5: 本地內部子模組相對匯入 (門面匯出，由底層到高階)
from .exceptions import CalculatorError, DivisionByZeroError
from .core.calculator import safe_divide

# 區塊 6: Package 全域元數據宣告 (Metadata)
__version__: Final[str] = "0.1.0"
__author__: Final[str] = "Matthew"

# 區塊 7: __all__ 公開白名單清單 (控制 from package import * 暴露符號)
__all__: list[str] = [
    "__version__",
    "__author__",
    "CalculatorError",
    "DivisionByZeroError",
    "safe_divide",
]

# 區塊 8: Package 層級初始化鉤子 (Initialization Hooks)
logging.getLogger(__name__).addHandler(logging.NullHandler())
```

---

### 子模組拓撲匯入順序法則

在 `__init__.py` 中匯入子模組時，必須遵循由底層到高階的拓撲順序：

```text
[底層] 1. types.py / exceptions.py  (純型別與例外，無內部依賴)
   │
   ▼
[中層] 2. base.py / interfaces.py   (抽象協定與基底類別)
   │
   ▼
[實作] 3. calculator.py / engine.py  (具體業務功能實作)
```

---

### 相對匯入語法速查表

在 Package 內部互相引用時，應一律採用明確的相對匯入語法：

| 相對語法範例 | 點號數量 | 尋找目標位置 | 適用情境 |
| :--- | :---: | :--- | :--- |
| `from . import config` | `1 個點` | **當前同一層目錄**下的 `config.py` | 匯入同層模組 |
| `from .base import Engine` | `1 個點` | **當前同一層目錄**下的 `base.py` 內物件 | 門面匯出同層類別 |
| `from ..utils import log` | `2 個點` | **上一層父目錄**下的 `utils/` 目錄 | 子模組調用通用工具 |
| `from ...core import db` | `3 個點` | **上兩層祖父目錄**下的 `core/` 目錄 | 深層子模組存取核心層 |

---

### 門面匯出實戰對照

- `[未設定門面匯出]`：外部使用者必須知曉內部檔案結構，匯入路徑冗長且易碎：
  ```python
  from my_project.core.calculator import safe_divide
  ```
- `[已設定門面匯出]`：在 `__init__.py` 完成封裝，外部直接從頂層簡潔引用：
  ```python
  from my_project import safe_divide
  ```

> **[生動比喻]**：  
> `__init__.py` 是辦公大樓的迎賓櫃檯。訪客無需親自登上高樓層尋找工程師，在大廳櫃檯即可取得核准對外發布的資料與服務。

### 實戰教學：使用 python-dotenv 讀取環境變數

#### 步驟 1：安裝套件
```shell
uv add python-dotenv
```

#### 步驟 2：編寫 .env 檔案
在專案根目錄下建立 `.env` 檔案（鍵值對格式，無須額外引號）：
```env
APP_ENV=development
DEBUG=True
PORT=8000
DATABASE_URL=sqlite:///./dev.db
API_KEY=sk-proj-demo-secret-key-123456
```

#### 步驟 3：在 Python 程式碼中載入並驗證
通常在專案的 `config.py` 中進行載入與驗證：

```python
# src/my_project/config.py

import os
from dotenv import load_dotenv

# 1. 搜尋並載入當前或上層目錄的 .env 檔案
load_dotenv()

# 2. 讀取環境變數並進行型別轉換
APP_ENV: str = os.getenv("APP_ENV", "development")
DEBUG: bool = os.getenv("DEBUG", "False").lower() == "true"
PORT: int = int(os.getenv("PORT", "8000"))
API_KEY: str | None = os.getenv("API_KEY")

# 3. 關鍵安全性防護驗證
if not API_KEY:
    raise ValueError("致命錯誤：未設定必要的 API_KEY 環境變數，系統拒絕啟動！")
```

> **[生動比喻]**：  
> `.env` 是保險箱的實體鑰匙，每位工程師各持一把；`.env.example` 則是鑰匙的形狀說明藍圖。

# 實戰除錯與核心天條

## 1. 循環匯入 (Circular Import) 致命死鎖

- **錯誤症狀**：直譯器拋出 `ImportError: cannot import name ... from partially initialized module`。
- **背後原理**：`__init__.py` 匯入了模組 A，而模組 A 又在頂部匯入 `__init__.py` 或模組 B。兩個模組在尚未完成初始化前互相等待對方定義符號，引發死鎖。
- **記憶口訣**：子模組嚴禁反向匯入 `__init__.py`，內部依賴走具體模組，門面匯出只做單向傳遞。

```python
# [錯誤寫法]：子模組從父級 package 的 __init__.py 倒著匯入
from my_project import safe_divide

# [正確寫法]：子模組直接引用同級或底層具體模組
from .calculator import safe_divide
```

---

## 2. 扁平結構 (Flat Layout) 引發測試偽陽性

- **錯誤症狀**：本地執行 `pytest` 全部通過，打包發布或他人透過 `pip install` 安裝後卻因遺漏依賴或靜態檔而崩潰。
- **背後原理**：Flat Layout 使得 Python 將專案根目錄自動注入 `sys.path[0]`，測試程式直接調用了未經打包安裝的生鮮程式碼。
- **記憶口訣**：原始碼必須封裝於 `src/`，測試前一律使用可編輯模式安裝至虛擬環境。

```shell
# [錯誤做法]：直接在 Flat Layout 根目錄裸跑測試
pytest

# [正確做法]：採用 Src Layout 並透過可編輯模式安裝後由 uv 執行
uv pip install -e ".[dev]"
uv run pytest
```

## 3. 私密金鑰洩漏至 Git 歷史紀錄

- **錯誤症狀**：API 金鑰遭網路爬蟲掃描竊取，即便後續刪除檔案，歷史 Commit 仍永久留存憑證。
- **背後原理**：在建立 `.gitignore` 前就將包含密鑰的 `.env` 加入 Git 暫存區追蹤。
- **記憶口訣**：先寫黑名單再存金鑰，倉庫只留範本檔，本機專屬實體鍵。

```shell
# [錯誤做法]：先 git add . 後才建立 .gitignore
git add .
touch .gitignore

# [正確做法]：初始化倉庫後第一時間建立 .gitignore 並驗證 .env 被忽略
touch .gitignore
git status --ignored
```

## 4. 全域環境污染與依賴版本衝突

- **錯誤症狀**：在系統全域環境執行 `pip install`，導致不同專案依賴版本相互覆蓋破壞。
- **背後原理**：未使用虛擬環境進行依賴隔離，多個專案共用全域套件庫。
- **記憶口訣**：一專案一虛擬環境，嚴禁全域安裝，統一使用 uv 隔離與管理。

```shell
# [錯誤做法]：使用全域 Python 環境安裝套件
pip install requests

# [正確做法]：每個專案獨立建立 .venv 並透過 uv 隔離管理
uv venv
uv add requests
```

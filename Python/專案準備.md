# 概念與原理

## Industry Standard 行業標準專案

開發專案時，將程式碼、測試、設定檔與文檔**結構化與模組化**的規範體系。

### 什麼是「單檔劇本 (Single-file Script)」？

初學者剛開始學習 Python 時，通常會在編輯器裡新建一個 `main.py` 或 `demo.py`。
開發者會把所有的變數、函式、爬蟲邏輯、資料庫連線甚至測試碼全部擠在這幾百行的單一檔案裡。
這種缺乏架構劃分的程式碼形式就稱為「單檔劇本」。

### 為什麼現代工程必須告別單檔劇本？

當專案從小玩具成長為真正的軟體產品時，單檔劇本會帶來致命的缺陷：

- **維護成本極高**：在數千行的單一檔案中修改邏輯，容易牽一髮而動全身。
- **無法多人協同**：多位工程師同時修改 `main.py` 時，提交 Git 會產生大量版本衝突 (Merge Conflict)。
- **無法模組化複用**：外部專案無法透過 `import` 引用特定函式，只能手動複製貼上。
- **無法自動化測試**：業務邏輯與執行入口混雜，無法針對單一功能編寫獨立單元測試 (Unit Test)。

> **[生動比喻]**：  
> 單檔劇本就像雜亂的玩具收納箱，剪刀、筆刷與零件全部塞在同一個格子裡。要找任何工具都必須把整個箱子倒出來。  
> 行業標準專案就像現代化汽車工廠，引擎、輪胎與電路車間各自獨立，最後在裝配線上透過標準介面組合。

## Src Layout 原始碼隔離架構

將專案真正要執行的 Python 原始碼統一收納在 `src/` 資料夾內部的工程設計模式。

### 什麼是 Src Layout？

Python 社群歷史上有兩種主流目錄架構：

1. **Flat Layout (扁平結構)**：直接把專案套件資料夾（例如 `my_project/`）放在專案最頂層的根目錄。
2. **Src Layout (源碼隔離結構)**：在根目錄下建立 `src/` 資料夾，並把 `my_project/` 封裝在 `src/` 內部。

現代 Python 官方打包指南 (PyPA) 與主流建置工具（如 `uv`、`hatch`、`setuptools`）一致推薦使用 **Src Layout**。

### 為什麼要多加一層 src/？（解決測試偽陽性陷阱）

當開發者在終端機執行 `pytest` 或執行 Python 程式時，Python 的模組搜尋路徑 (`sys.path`) 預設會**將當前的工作目錄 (Current Working Directory) 自動加入搜尋清單首位**。

- **Flat Layout 的隱藏災難**：  
  根目錄下直接存在 `my_project/` 資料夾。執行 `pytest` 時，直譯器會直接匯入根目錄下**未經打包、未經安裝的原始碼**。  
  這會引發「測試偽陽性 (Import Paranoia)」：測試全部通過，但使用者透過 `pip install` 安裝套件時，卻因為遺漏非 `.py` 靜態檔案或設定檔而直接崩潰。
- **Src Layout 的防禦機制**：  
  根目錄下沒有 `my_project/` 資料夾，原始碼被隔離在 `src/` 內部。如果在根目錄直接執行測試，直譯器會拋出找不到模組的錯誤。  
  這迫使開發者必須先將套件以**可編輯模式 (Editable Mode)** 安裝至[[終端指令#虛擬環境|虛擬環境]]中。此舉確保開發測試環境與最終使用者安裝環境完全一致。

> **[生動比喻]**：  
> `src/` 就像工廠的保密生產車間，根目錄則是對外開放的展示門市。  
> 若沒有 `src/` 隔離，測試人員就會直接拿生產線上塗料未乾的半成品進行檢驗；有了 `src/`，產品必須通過標準包裝與出廠檢驗，才能進行驗證與交付。

```text
│       │   ├── __init__.py

│           ├── __init__.py
│           └── helpers.py

│   ├── conftest.py            # pytest 共用 Fixture 與測試環境全域設定

│   │   └── test_engine.py
│   └── integration/           # 整合測試 (Integration Tests)
│       └── test_api_client.py
├── .env                       # [私密環境變數] 真實金鑰與密碼 (絕對不可進 Git)
├── .env.example               # [環境變數範本] 公開的金鑰結構與預設值範本
├── .gitignore                 # Git 版本控制黑名單：指定要忽略的暫存檔與秘密檔
├── LICENSE                    # 開源授權條款文字檔 (如 MIT, Apache 2.0)
├── pyproject.toml             # [專案中央指揮總部] 建置工具、套件依賴與開發工具設定
```

# 專案環境初始化標準起手式流程

從零啟動一個現代 Python 專案時，環境建置與依賴管理是決定後續工程穩定度的核心基石。以下為標準七步流程：

### Step 1：建立專案目錄與 Git 初始化

在終端機建立專案專屬根目錄，並立刻啟動版本控制：

```shell
# 1. 建立專案目錄並進入
mkdir my_project
cd my_project

# 2. 初始化 Git 倉庫
git init
```

---

### Step 2：建立隔離虛擬環境 (.venv)

使用現代極速 `uv` 工具建立專屬環境，支援直接指定特定 Python 版本：

```shell
# 1. 使用當前系統 Python 建立 .venv 虛擬環境
uv venv

# 2. 或指定特定 Python 版本建立環境 (例如 Python 3.12)
uv venv --python 3.12
```

---

### Step 3：一鍵生成 Src Layout 標準目錄與空白檔案

在專案根目錄下，透過 Shell 命令一鍵建立符合 Src Layout 的標準結構：

```shell
# 1. 建立 src 核心目錄、測試目錄、文件目錄與維運目錄
mkdir -p src/my_project/core tests/unit tests/integration docs scripts

# 2. 建立 package 標記檔案與進入點
touch src/my_project/__init__.py
touch src/my_project/__main__.py
touch src/my_project/py.typed
touch src/my_project/core/__init__.py

# 3. 建立測試環境設定檔
touch tests/__init__.py
touch tests/conftest.py
```

---

### Step 4：配置版本控制黑名單與環境變數範本

在進行任何代碼編寫前，必須先配置 `.gitignore` 與 `.env.example`，防止敏感資訊外洩：

```shell
# 1. 建立 .gitignore 檔案
cat << EOF > .gitignore
# Python 快取
__pycache__/
*.py[cod]
*$py.class

# 虛擬環境
.venv/
venv/
ENV/

# 敏感環境變數
.env
.env.local

# 測試與覆蓋率報告
.pytest_cache/
.coverage
htmlcov/
.mypy_cache/
.ruff_cache/

# 作業系統垃圾檔案
.DS_Store
Thumbs.db
EOF

# 2. 建立公開環境變數範本
cat << EOF > .env.example
APP_ENV=development
DEBUG=True
PORT=8000
API_KEY=your_secret_api_key_here
DATABASE_URL=sqlite:///./dev.db
EOF

# 3. 複製出本機實際使用的私密環境變數檔
cp .env.example .env
```

---

### Step 5：撰寫 pyproject.toml 專案配置

在專案根目錄建立 `pyproject.toml`，集中定義專案元數據、建置系統與開發工具：

```toml
[build-system]
requires = ["setuptools>=61.0"]
build-backend = "setuptools.build_meta"

[project]
name = "my_project"
version = "0.1.0"
description = "符合現代行業標準的完整 Python 專案"
readme = "README.md"
requires-python = ">=3.10"
license = { text = "MIT" }
authors = [
    { name = "Matthew", email = "matthew@example.com" }
]
dependencies = [
    "python-dotenv>=1.0.0",
]

[project.optional-dependencies]
dev = [
    "pytest>=8.0.0",
    "pytest-cov>=4.1.0",
    "mypy>=1.8.0",
    "ruff>=0.2.0",
]

[project.scripts]
my-cli = "my_project.__main__:main"

[tool.pytest.ini_options]
minversion = "8.0"
addopts = "-ra -q"
testpaths = ["tests"]
pythonpath = ["src"]
```

---

### Step 6：新增專案依賴與環境同步

透過 `uv add` 新增套件，工具會自動解析依賴並寫入 `pyproject.toml`：

```shell
# 1. 新增正式生產環境依賴
uv add python-dotenv requests

# 2. 新增開發與測試專用依賴
uv add --dev pytest pytest-cov ruff mypy

# 3. 以可編輯模式安裝當前專案與依賴
uv pip install -e ".[dev]"
```

---

### Step 7：免啟動環境執行與自動化驗證

藉由 `uv run`，命令列可以在不手動啟動虛擬環境的前提下，直接調用環境內的二進位執行檔或模組：

```shell
# 1. 執行專案自訂 CLI 指令
uv run my-cli

# 2. 透過模組路徑啟動主程式
uv run python -m my_project

# 3. 執行自動化測試
uv run pytest

# 4. 執行代碼靜態檢查與格式化
uv run ruff check
uv run ruff format

# 5. 執行嚴格型別檢查
uv run mypy src
```

# 現代工具鏈指令詳解

##### uv venv 虛擬環境建立

- **使用時機**：開啟新專案或需要為既有專案建立獨立隔離的 Python 運行包廂時使用。
- **語法**：`uv venv [PATH] [--python VERSION]`
- **參數說明**：
  - `PATH`：虛擬環境存放目錄路徑，預設為 `.venv`。
  - `--python`：指定 Python 直譯器版本（如 `3.11`、`3.12`）。若本地未安裝，`uv` 會自動下載並建立。
- **回傳成果**：在目標路徑生成完整的虛擬環境目錄結構。

```shell
# 1. 使用當前預設 Python 建立 .venv
uv venv

# 2. 指定 Python 3.12 建立虛擬環境
uv venv --python 3.12
```

---

##### uv add 依賴套件安裝與寫入

- **使用時機**：專案需要引入第三方開源套件時使用。會自動解析相容版本並將依賴項目寫入 `pyproject.toml`。
- **語法**：`uv add [PACKAGE...] [--dev]`
- **參數說明**：
  - `PACKAGE`：要安裝的套件名稱（支援版本約束，如 `requests>=2.31.0`）。
  - `--dev`：標記為開發環境專用依賴（寫入 `optional-dependencies.dev`）。
- **回傳成果**：更新 `pyproject.toml` 與 `uv.lock`，並將套件安裝至 `.venv`。

```shell
# 1. 安裝正式生產依賴
uv add requests pydantic

# 2. 安裝開發與測試依賴
uv add --dev pytest ruff mypy
```

##### uv remove 依賴套件移除

- **使用時機**：專案淘汰某個第三方套件時使用。會同步清理設定檔與環境。
- **語法**：`uv remove [PACKAGE...] [--dev]`
- **參數說明**：
  - `PACKAGE`：要移除的套件名稱。
  - `--dev`：自開發依賴群組中移除。
- **回傳成果**：自 `pyproject.toml` 與 `uv.lock` 中刪除該套件宣告，並自虛擬環境中解除安裝。

```shell
# 移除指定套件
uv remove requests
```

##### uv lock 跨平台依賴鎖定

- **使用時機**：在部署發布前，或團隊需要統一所有人電腦上的精確套件版本時使用。
- **語法**：`uv lock [--upgrade]`
- **參數說明**：
  - `--upgrade`：可選參數，強制將所有依賴升級至符合約束的最最新版。
- **回傳成果**：生成或更新 `uv.lock` 確定性依賴圖譜檔案。

```shell
# 生成全專案版本鎖定檔
uv lock
```

##### uv sync 虛擬環境依賴同步

- **使用時機**：團隊成員剛從 Git 複製專案，或在 CI/CD 伺服器建置乾淨測試環境時使用。
- **語法**：`uv sync [--all-extras]`
- **參數說明**：
  - `--all-extras`：可選參數，同時安裝所有可選擴充依賴群組。
- **回傳成果**：將本機 `.venv` 嚴格同步至與 `uv.lock` 完全一致的狀態。

```shell
# 一鍵同步環境
uv sync
```

##### uv run 免啟動環境命令執行

- **使用時機**：需要在虛擬環境內執行腳本、CLI 工具或測試命令，但不想手動執行 `source .venv/bin/activate` 時使用。
- **語法**：`uv run [COMMAND] [ARGS...]`
- **參數說明**：
  - `COMMAND`：要執行的可執行檔或 Python 命令（如 `pytest`、`python`、`ruff`）。
- **回傳成果**：在隔離環境內部執行該指令，並將標準輸出直接傳回當前終端機。

```shell
# 1. 免啟動環境執行測試
uv run pytest

# 2. 免啟動環境執行模組
uv run python -m my_project
```

##### pip install -e 可編輯模式安裝

- **使用時機**：搭配 Src Layout 開發本地 Package 時使用。建立符號連結，使原始碼的任何修改即時反映至環境中。
- **語法**：`uv pip install -e ".[dev]"`

  - `-e`：Editable Mode（可編輯模式）標記。
  - `.[dev]`：安裝當前目錄套件本體，並一併附帶安裝 `dev` 開發相依群組。
- **回傳成果**：將當前套件連結至虛擬環境的 `site-packages`。

```shell
# 以可編輯模式安裝當前專案
uv pip install -e ".[dev]"
```

- **檔案職責**：現代 Python 專案最重要的核心設定檔（PEP 518 / PEP 621）。集中管理依賴、建置系統與所有開發工具配置。

  - `[tool.xxx]`：集中管理 `pytest`、`ruff`、`mypy` 等工具參數。

> **[生動比喻]**：  
> `pyproject.toml` 是專案的中央指揮總部與數位身分證，所有關於專案身分、零件需求與工作準則的指令皆在此集中發布。

```toml
name = "my_project"

    { name = "Matthew", email = "matthew@example.com" }
]

    "python-dotenv>=1.0.0",
]

[project.optional-dependencies]

    "pytest>=8.0.0",
    "pytest-cov>=4.1.0",
    "mypy>=1.8.0",
    "ruff>=0.2.0",
]

[project.scripts]
my-cli = "my_project.__main__:main"

[tool.pytest.ini_options]
minversion = "8.0"
addopts = "-ra -q"
testpaths = ["tests"]
pythonpath = ["src"]
```

##### __init__.py 套件入口與門面匯出

- **檔案職責**：標記 Python Package 身分，並作為對外匯出的控制門面。
- **載入生命週期 4 階段**：
  1. 搜尋定位：直譯器在 `sys.path` 找到目標套件目錄。
  2. 頂層執行：直譯器由上至下完整執行 `__init__.py`。
  3. 觸發內部匯入：依序執行內部的相對匯入語法。
  4. 註冊快取：將模組物件登錄至 `sys.modules` 快取。

```python
# 區塊 1: 模組文件字串 (Package Docstring)
"""
My Project Core Package
~~~~~~~~~~~~~~~~~~~~~~~
提供核心運算引擎與輔助工具介面。
"""

# 區塊 2: 語言特性開關 (__future__ Imports)
from __future__ import annotations

# 區塊 3: Python 原生標準庫匯入 (Standard Library Imports)
import logging
import sys
from typing import Final

# 區塊 4: 第三方套件匯入 (Third-Party Imports)
import pydantic

# 區塊 5: 本地內部子模組相對匯入 (門面匯出，由底層到高階)
from .exceptions import CalculatorError, DivisionByZeroError
from .core.calculator import safe_divide

# 區塊 6: Package 全域元數據宣告 (Metadata)
__version__: Final[str] = "0.1.0"
__author__: Final[str] = "Matthew"

# 區塊 7: __all__ 公開白名單清單 (控制 from package import * 暴露符號)
__all__: list[str] = [
    "__version__",
    "__author__",
    "CalculatorError",
    "DivisionByZeroError",
    "safe_divide",
]

# 區塊 8: Package 層級初始化鉤子 (Initialization Hooks)
logging.getLogger(__name__).addHandler(logging.NullHandler())
```

- **相對匯入語法速查表**：

| 相對語法範例 | 點號數量 | 尋找目標位置 | 適用情境 |
| :--- | :---: | :--- | :--- |
| `from . import config` | `1 個點` | **當前同一層目錄**下的 `config.py` | 匯入同層模組 |
| `from .base import Engine` | `1 個點` | **當前同一層目錄**下的 `base.py` 內物件 | 門面匯出同層類別 |
| `from ..utils import log` | `2 個點` | **上一層父目錄**下的 `utils/` 目錄 | 子模組調用通用工具 |
| `from ...core import db` | `3 個點` | **上兩層祖父目錄**下的 `core/` 目錄 | 深層子模組存取核心層 |

# 實戰除錯與核心天條

## 1. 循環匯入 (Circular Import) 致命死鎖

- **錯誤症狀**：直譯器拋出 `ImportError: cannot import name ... from partially initialized module`。
- **背後原理**：`__init__.py` 匯入了模組 A，而模組 A 又在頂部匯入 `__init__.py` 或模組 B。兩個模組在尚未完成初始化前互相等待對方定義符號，引發死鎖。
- **記憶口訣**：子模組嚴禁反向匯入 `__init__.py`，內部依賴走具體模組，門面匯出只做單向傳遞。

```python
# [錯誤寫法]：子模組從父級 package 的 __init__.py 倒著匯入
from my_project import safe_divide

# [正確寫法]：子模組直接引用同級或底層具體模組
from .calculator import safe_divide
```

---

## 2. 扁平結構 (Flat Layout) 引發測試偽陽性

- **錯誤症狀**：本地執行 `pytest` 全部通過，打包發布或他人透過 `pip install` 安裝後卻因遺漏依賴或靜態檔而崩潰。
- **背後原理**：Flat Layout 使得 Python 將專案根目錄自動注入 `sys.path[0]`，測試程式直接調用了未經打包安裝的生鮮程式碼。
- **記憶口訣**：原始碼必須封裝於 `src/`，測試前一律使用可編輯模式安裝至虛擬環境。

```shell
# [錯誤做法]：直接在 Flat Layout 根目錄裸跑測試
pytest

# [正確做法]：採用 Src Layout 並透過可編輯模式安裝後由 uv 執行
uv pip install -e ".[dev]"
uv run pytest
```

## 3. 私密金鑰洩漏至 Git 歷史紀錄

- **錯誤症狀**：API 金鑰遭網路爬蟲掃描竊取，即便後續刪除檔案，歷史 Commit 仍永久留存憑證。
- **背後原理**：在建立 `.gitignore` 前就將包含密鑰的 `.env` 加入 Git 暫存區追蹤。
- **記憶口訣**：先寫黑名單再存金鑰，倉庫只留範本檔，本機專屬實體鍵。

```shell
# [錯誤做法]：先 git add . 後才建立 .gitignore
git add .
touch .gitignore

# [正確做法]：初始化倉庫後第一時間建立 .gitignore 並驗證 .env 被忽略
touch .gitignore
git status --ignored
```

## 4. 全域環境污染與依賴版本衝突

- **錯誤症狀**：在系統全域環境執行 `pip install`，導致不同專案依賴版本相互覆蓋破壞。
- **背後原理**：未使用虛擬環境進行依賴隔離，多個專案共用全域套件庫。
- **記憶口訣**：一專案一虛擬環境，嚴禁全域安裝，統一使用 uv 隔離與管理。

```shell
# [錯誤做法]：使用全域 Python 環境安裝套件
pip install requests

# [正確做法]：每個專案獨立建立 .venv 並透過 uv 隔離管理
uv venv
uv add requests
```

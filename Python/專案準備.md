# 概念與原理

## Industry Standard 行業標準專案

開發專案時，將程式碼、測試、設定檔與文檔**結構化與模組化**的規範體系

### 什麼是「單檔劇本 (Single-file Script)」？
初學者剛開始學習 Python 時，通常會在編輯器裡新建一個 `main.py` 或 `demo.py`，把所有的變數、函式、爬蟲邏輯、資料庫連線甚至測試碼全部擠在這幾百行的單一檔案裡。這就叫做「單檔劇本」。

### 為什麼現代工程必須告別單檔劇本？
當專案從小玩具成長為真正的軟體產品時，單檔劇本會帶來致命的缺陷：

- **維護噩夢**：要在幾千行的檔案中修改一個小 bug，就像在海裡撈針，牽一髮而動全身
- **無法團隊分工**：多位工程師如果同時修改 `main.py`，在提交 Git 時會產生排山倒海的**版本衝突 (Merge Conflict)**
- **無法重複使用**：如果另一個專案想借用你寫好的「資料處理函式」，因為程式碼全部綁在 `main.py` 裡，你只能手動「複製貼上」，無法透過 `import` 來模組化引用
- **無法自動化測試**：業務邏輯與程式執行入口混在一起，無法針對單一功能編寫獨立的單元測試 (Unit Test)

> **生活化比喻**：  
> 把單檔劇本想像成**雜亂的玩具手作文具箱**：螺絲釘、水彩筆、剪刀、垃圾全部塞在同一個格子裡，要找東西必須全倒出來；  
> 而符合行業標準的專案結構，就像是**現代化的汽車製造工廠**：引擎車間、輪胎車間、電路車間（各模組）各自獨立運作，最後在組裝線上透過標準化介面組合

## Src Layout 原始碼隔離架構

將專案真正要執行的 Python 原始碼統一放在 `src/` 資料夾內部的工程設計模式

### 什麼是 Src Layout？
Python 社群發展歷史上有兩種主流的專案結構：
1. **Flat Layout (扁平結構)**：直接把專案 package 資料夾（例如 `my_project/`）隨手扔在專案的最高層根目錄
2. **Src Layout (源碼隔離結構)**：在根目錄下建立一個名為 `src` 的資料夾，並把 `my_project/` 放在 `src/` 裡面

現代 Python 官方打包指南 (PyPA) 與幾乎所有主流建置工具（如 `setuptools`、`hatch`、`poetry`、`uv`）一致強烈推薦使用 **Src Layout**。

### 為什麼要多加一層 `src/`？（解決測試偽陽性陷阱）

當你在終端機執行 `pytest` 或執行 Python 程式時，Python 的核心模組搜尋路徑 (`sys.path`) 預設會**把當前的「工作目錄 (Current Working Directory)」自動塞進搜尋清單的第一個位置**。

#### Flat Layout 的隱藏災難：
如果使用扁平結構，專案根目錄下直接就有 `my_project/` 資料夾。當你執行 `pytest` 時，Python 會直接載入根目錄下**未經打包、未經安裝的原始碼**。  
這會導致一個恐怖的現象——**「測試偽陽性 (Import Paranoia)」**：
你以為測試全都通過了，結果使用者透過 `pip install` 安裝你的套件時，卻因為你忘記包含某個非 `.py` 靜態檔案或設定檔而直接崩潰！

#### Src Layout 的完美防禦：
當你使用了 `src/` 結構，專案根目錄下**沒有** `my_project/` 資料夾（它被鎖在 `src/` 內部）。  
此時如果在根目錄直接執行測試，Python 會因為在根目錄找不到 `my_project` 而直接報錯。這迫使開發者必須先透過：
```shell
pip install -e .
```
將專案以**可編輯模式 (Editable Mode)** 正式安裝到[[終端指令#虛擬環境|虛擬環境]]中。這樣能確保你在開發階段運行的測試，與最終使用者安裝後的運行環境**完全一模一樣**！

> **生活化比喻**：  
> 想像 `src/` 就像是**工廠的「保密生產車間」**；根目錄則是**對外開放的門市專櫃**。  
> 如果沒有 `src/`（Flat Layout），測試人員就會直接拿生產線上塗料還沒乾的半成品去測試；有了 `src/`，產品必須先通過標準包裝與出廠檢驗（安裝到虛擬環境），才能拿去測試與販售

# 現代 Python 專案目錄結構全貌

以下為一個符合現代 Python 最高行業標準（Src Layout）的完整專案結構樹狀視圖：

```text
my_awesome_project/            # 【專案根目錄】專案的最頂層資料夾
├── .git/                      # Git 版本控制內部追蹤目錄 (自動生成，不可手動修改)
├── .github/                   # GitHub 平台專用資料夾
│   └── workflows/             # CI/CD 自動化工作流程定義檔 (如 Actions 腳本)
│       └── ci.yml
├── docs/                      # 【專案說明文件目錄】存放技術文件與 API 手冊
│   ├── index.md
│   └── setup_guide.md
├── scripts/                   # 【維運腳本目錄】獨立運行的輔助小工具與腳本
│   └── init_db.py
├── src/                       # 【原始碼隔離層】防止測試偽陽性的核心保護罩
│   └── my_awesome_project/    # 【Package 本體】真正要被打包與發布的 Python 包 (蛇形命名)
│       ├── __init__.py        # 包入口：定義對外暴露的 API 與版本號 (__version__)
│       ├── __main__.py        # CLI 執行入口：支援 python -m my_awesome_project 啟動
│       ├── py.typed           # PEP 561 標記：告知第三方工具本套件支援[[Python#型別注記|型別註記]]
│       ├── config.py          # 設定檔載入器：讀取 .env 或系統環境變數
│       ├── exceptions.py      # 自訂異常類別：定義專案專屬的 Exception 體系
│       ├── core/              # 核心業務邏輯子包
│       │   ├── __init__.py
│       │   └── engine.py
│       ├── services/          # 外部服務整合子包 (API Client, 資料庫連線)
│       │   ├── __init__.py
│       │   └── api_client.py
│       └── utils/             # 通用小工具子包 (Helpers, 日誌處理)
│           ├── __init__.py
│           └── helpers.py
├── tests/                     # 【自動化測試目錄】存放所有 pytest 測試檔案
│   ├── __init__.py
│   ├── conftest.py            # pytest 共用 Fixture 與測試環境全域設定
│   ├── unit/                  # 單元測試 (Unit Tests)
│   │   └── test_engine.py
│   └── integration/           # 整合測試 (Integration Tests)
│       └── test_api_client.py
├── .env                       # 【私密環境變數】真實金鑰與密碼 (絕對不可進 Git)
├── .env.example               # 【環境變數範本】公開的金鑰結構與預設值範本
├── .gitignore                 # Git 版本控制黑名單：指定要忽略的垃圾檔與秘密檔
├── LICENSE                    # 開源授權條款文字檔 (如 MIT, Apache 2.0)
├── pyproject.toml             # 【專案中央指揮總部】建置工具、套件依賴與開發工具設定
└── README.md                  # 【專案門面履歷表】簡介、安裝步驟與快速上手指南
```

# 每個資料夾與檔案的詳細解密與職責說明

以下針對專案中的**每一個資料夾與關鍵檔案**進行深度的剖析，徹底解答「它是什麼」、「在做什麼」、「該放什麼」與「絕對不能放什麼」：

---
## 【目錄篇】

### 1. `src/` (Source Code 原始碼目錄)

#### 名字由來
`src` 是英文 **Source (來源 / 原始碼)** 的標準縮寫。在 C++、Java、Rust、Go 等所有現代程式語言中，`src/` 都是預定用來存放原始碼的標準名稱。

#### 它是什麼？在做什麼？
`src/` 是專案原始碼的**防護箱與隔離外殼**。它的核心目的就是將「真正要運行的產品程式碼」與「根目錄下的各種設定檔、測試檔、自動化腳本」進行物理上的徹底分離。

#### 裡面該放什麼資料？
- 只能存放**專案最終要打包發布或運行的 Python Package (包)**。例如 `src/my_awesome_project/`。

#### 絕對不能放什麼資料？
- ❌ **絕對不能放測試檔案**（測試檔應放在 `tests/`）
- ❌ **絕對不能放秘密金鑰或 `.env` 檔**
- ❌ **絕對不能放運作產生的垃圾資料或數據集 (Data)**

> **白話比喻**：`src/` 就是金庫的**防彈玻璃外罩**，確保只有經過授權的產品程式碼能待在裡面，外面的雜物完全進不去

---
### 2. `src/專案名稱/` (Package 本體)

#### 名字由來
這是你專案的真正名稱，**必須使用蛇形命名 (`snake_case`)**，例如 `my_awesome_project`（不能包含減號 `-` 或空格，否則 Python 無法 `import`）。

#### 它是什麼？在做什麼？
這是專案業務邏輯的**大本營**。當其他開發者執行 `pip install your-package` 時，被安裝到他們電腦裡的，就是這個資料夾內部的所有程式碼。

#### 裡面應該如何劃分內部結構？
- `__init__.py`：包的門面與版本宣告
- `__main__.py`：CLI 命令列執行入口
- `config.py`：讀取與驗證環境變數
- `exceptions.py`：定義專案內部的自訂錯誤型態
- `core/`：存放專案最核心、最純粹的業務邏輯或演算法
- `services/`：存放與外部系統打交道的程式碼（如 API 呼叫、資料庫連線、Redis 快取）
- `utils/`：存放通用的輔助函式（如時間格式化、字串處理）

> **白話比喻**：這是汽車的**引擎總成**，裡面分工明確，火星塞、汽缸、皮帶各有專屬的附屬位置

---
### 3. `tests/` (測試目錄)

#### 名字由來
`tests` 即英文**測試 (Test)** 的複數形式。現代 Python 測試框架（如 `pytest`）預設會自動掃描名為 `tests` 的資料夾。

#### 它是什麼？在做什麼？
`tests/` 是專案的**品質檢驗站與安全網**。所有用來驗證程式碼功能是否正確、修改後有沒有撞爛舊功能的自動化測試腳本，通通放在這裡。

#### 裡面該放什麼資料？
- `conftest.py`：`pytest` 的全域共用測試環境設定檔與共用假資料 (Fixtures)
- `unit/` (單元測試)：針對單一函式、單一類別進行的微型快速測試
- `integration/` (整合測試)：測試多個模組串接、資料庫連線或 API 調用的完整流程測試
- 測試檔案名稱**必須以 `test_` 開頭**（例如 `test_calculator.py`），`pytest` 才能自動辨識

#### 絕對不能放什麼資料？
- ❌ **絕對不能放產品線真正的業務邏輯**
- ❌ **絕對不能放真實的生產環境密碼與金鑰**

> **白話比喻**：`tests/` 就是汽車發射前的**碰撞測試實驗室**，所有零件在出廠前都要在這裡被折磨摧殘過，確定沒問題才能上路

---
### 4. `docs/` (文件目錄)

#### 名字由來
`docs` 是英文 **Documentation (文件 / 文檔)** 的縮寫。

#### 它是什麼？在做什麼？
`docs/` 是專案的**知識庫與使用手冊說明書**。當新人加入團隊，或是外部開發者想使用你的開源套件時，`docs/` 提供了除了程式碼之外的最詳盡導覽。

#### 裡面該放什麼資料？
- Markdown 格式的技術文件（如 `setup.md`、`architecture.md`）
- 靜態文件生成工具（如 MkDocs 或 Sphinx）的設定檔 (`mkdocs.yml`)
- 系統架構圖、流程圖圖片（如 `.png` 或 `.svg`）

> **白話比喻**：`docs/` 就是買新家電時附贈的那本**繁體中文詳細使用說明書**

---
### 5. `scripts/` (腳本目錄)

#### 名字由來
`scripts` 即英文**腳本 (Script)** 的複數形式。

#### 它是什麼？在做什麼？
`scripts/` 是專案的**後勤維護工具箱**。這裡存放的是給「開發者」或「維運工程師 (DevOps)」手動執行的小工具，這些工具**不會**被打包發布給最終使用者。

#### 裡面該放什麼資料？
- 資料庫初始化與測試資料植入腳本（如 `init_db.py`、`seed_data.py`）
- 數據清理、日誌分析小腳本
- 自動化部署與建置 Shell 腳本（如 `deploy.sh`）

#### 絕對不能放什麼資料？
- ❌ **絕對不能放會被 `src/` 內部的業務邏輯 `import` 的模組**（這會造成依賴混亂）

> **白話比喻**：`scripts/` 就是保養廠裡的**千斤頂與特規維修工具**，平時不隨車攜帶，只有保養維修時才會拿出來用

---
### 6. `.github/workflows/` (CI/CD 自動化流程目錄)

#### 名字由來
這是 GitHub 平台規定的固定隱藏目錄路徑。`workflows` 代表**工作流程**。

#### 它是什麼？在做什麼？
這是專案的**雲端自動化機器人管家 (CI/CD 流水線)**。只要你將程式碼 Push 到 GitHub，GitHub Actions 機器人就會自動觸發這個目錄下的 YAML 設定檔，自動開一台雲端電腦幫你跑 `pytest` 測試與 `ruff` 程式碼檢查！

#### 裡面該放什麼資料？
- `.yml` 或 `.yaml` 格式的工作流程定義檔（例如 `ci.yml`）

> **白話比喻**：這就像是**工廠的自動化品檢傳送帶**，只要你一交作業，機器手臂自動抓去掃描檢查，有問題立刻發郵件嗶嗶叫警報

## 【關鍵檔案篇】

### 1. `__init__.py`

#### 名字由來
`init` 是 **Initialize (初始化)** 的縮寫，前後雙底線（`__`）代表這是 Python 語言層級的魔術檔案 (Magic File)。

#### 它是什麼？在做什麼？
1. **標記身分**：告訴 Python 直譯器「這個資料夾不是普通資料夾，而是一個 **Package (包)**！」
2. **控制對外 API 門面 (Package Export Door)**：當其他人 `import my_project` 或 `import my_project.providers` 時，Python 執行的就是該資料夾下的 `__init__.py`。你可以將深層子模組的類別匯出，並用 `__all__` 變數控制暴露公開清單。

---

#### 🔄 `__init__.py` 的載入生命週期與匯入順序

理解 Python 在 `import` 一個 Package 時的**底層執行順序**，是構建大型架構與避免循環引用的第一步：

##### 1. 直譯器載入 Package 的 4 大階段：

```text
外部呼叫: import my_package
   │
   ▼
1. 搜尋定位 ➔ Python 在 sys.path 中找到 my_package/ 目錄
   │
   ▼
2. 頂層執行 ➔ 直譯器由上至下 (Top-to-Bottom) 完整執行 my_package/__init__.py 檔案
   │
   ▼
3. 觸發內部匯入 ➔ 執行 __init__.py 內的 from .submodule import Class（依序載入子模組）
   │
   ▼
4. 註冊快取 ➔ 將初始化完成的 Package 物件存入 sys.modules 快取中，結束匯入
```

> **⚠️ 核心觀念**：  
> 當外部 `import my_package` 時，`my_package/__init__.py` 是**第一個被執行的程式碼**。只有當 `__init__.py` 內的所有程式碼與匯入全部跑完，這個 Package 才算「真正存在」！

---

##### 2. `__init__.py` 內部程式碼標準排列順序 (PEP 8 規範)

一個結構嚴謹、符合工業級標準的 `__init__.py`，其內部程式碼應**嚴格遵循由上至下的 8 大標準順序**排列：

```python
# ==============================================================================
# 區塊 1: 模組文件字串 (Package Docstring) - 說明此 Package 的功能與用途
# ==============================================================================
"""
MiniClaude Core Engine Package
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
提供大語言模型調用、工具註冊與上下文管理核心引擎。
"""

# ==============================================================================
# 區塊 2: 語言特性開關 (__future__ Imports) - 必須位在所有程式碼的最頂部
# ==============================================================================
from __future__ import annotations

# ==============================================================================
# 區塊 3: Python 原生標準庫匯入 (Standard Library Imports) - 按字母順序排列
# ==============================================================================
import logging
import sys
from typing import Final

# ==============================================================================
# 區塊 4: 第三方套件匯入 (Third-Party Imports) - 按字母順序排列
# ==============================================================================
import pydantic
from rich.console import Console

# ==============================================================================
# 區塊 5: 本地內部子模組相對匯入 (Local Module Imports / 門面匯出 ⭐)
# ⚠️ 匯入順序原則：先匯入「底層基底與型別」，再匯入「高階實作」！
# ==============================================================================
# 5.1 先匯入底層型別與自訂異常 (無任何內部依賴)
from .exceptions import MiniClaudeError, ProviderNotFoundError
from .types import ToolCall, LLMResponse

# 5.2 再匯入抽象介面與基底類別
from .base import BaseProvider, BaseTool

# 5.3 最後匯入具體實作與高階引擎 (依賴上述基底)
from .gemini_provider import GeminiProvider
from .engine import AgentEngine

# ==============================================================================
# 區塊 6: Package 全域元數據宣告 (Metadata)
# ==============================================================================
__version__: Final[str] = "1.0.0"
__author__: Final[str] = "Matthew"
__license__: Final[str] = "MIT"

# ==============================================================================
# 區塊 7: __all__ 公開白名單清單 (嚴格控制 from my_package import * 暴露的符號)
# ==============================================================================
__all__: list[str] = [
    # 元數據
    "__version__",
    "__author__",
    # 核心類別
    "AgentEngine",
    "BaseProvider",
    "BaseTool",
    "GeminiProvider",
    # 資料結構
    "ToolCall",
    "LLMResponse",
    # 異常類別
    "MiniClaudeError",
    "ProviderNotFoundError",
]

# ==============================================================================
# 區塊 8: 可選的 Package 層級初始化鉤子 (Initialization Hooks)
# ==============================================================================
# 建立預設 NullHandler，防止外部在未設定日誌時噴出 No handler found 警告
logging.getLogger(__name__).addHandler(logging.NullHandler())
```

---

##### 3. 子模組之間的「拓撲匯入順序」黃金法則

在 `__init__.py` 中匯入內部子模組時，**必須依循由底層到高層的拓撲順序 (Topological Dependency Order)**，否則極易觸發 Python 的未初始化異常：

```text
【最底層】 1. types.py / exceptions.py  （純資料型別與錯誤類別，不依賴任何內部模組）
    │
    ▼
【中間層】 2. base.py / interfaces.py   （抽象父類別與 Protocol 協議，僅依賴 types）
    │
    ▼
【實作層】 3. provider.py / parser.py    （具體功能實作，繼承自 base）
    │
    ▼
【頂層層】 4. engine.py / pipeline.py   （組裝所有實作的大腦引擎）
```

---

##### 4. 相對匯入語法速查（點號 `.` 的層級意義）

在 `__init__.py` 內部匯入同專案其他檔案時，**永遠使用相對導入 (Explicit Relative Imports)**：

| 相對語法 | 點號數量 | 尋找路徑 | 適用情境範例 |
| :--- | :---: | :--- | :--- |
| `from . import config` | `1 個點` | **當前同一層目錄**下的 `config.py` | 同包內匯入同層模組 |
| `from .base import Engine` | `1 個點` | **當前同一層目錄**下的 `base.py` 裡面的 `Engine` | 門面匯出同層類別 |
| `from ..utils import log` | `2 個點` | **上一層父目錄**下的 `utils/` 資料夾 | 子包向外調用通用工具 |
| `from ...core import db` | `3 個點` | **上兩層祖父目錄**下的 `core/` 資料夾 | 深層子模組回溯核心層 |

---

#### 🛠️ 實戰教學：為什麼要在 `__init__.py` 寫門面匯出？
- ❌ **未設定門面匯出**（外部必須暴露深層檔名 `base.py`，極度冗長）：
  ```python
  from miniclaude.providers.base import LLMProvider, ToolCall, LLMResponse
  from miniclaude.providers.gemini_provider import GeminiProvider
  ```
- ✅ **在 `__init__.py` 寫好門面匯出與 `__all__`**：
  ```python
  # src/miniclaude/providers/__init__.py
  from .base import LLMProvider, ToolCall, LLMResponse
  from .gemini_provider import GeminiProvider

  __all__ = ["LLMProvider", "ToolCall", "LLMResponse", "GeminiProvider"]
  ```
- 🌟 **外部導入乾淨漂亮**：
  ```python
  from miniclaude.providers import GeminiProvider, ToolCall
  ```

> **⚠️ 循環匯入 (Circular Import) 致命死鎖天條**：  
> **現象**：若 `__init__.py` 匯入了 `module_a.py`，而 `module_a.py` 的頂部又寫了 `from . import something` 或 `import my_package`，Python 會因為兩者互相等待對方初始化而拋出 `ImportError: cannot import name ... from partially initialized module`！  
> **鐵律**：  
> 1. 子模組內部**嚴禁從 `__init__.py` 倒著匯入東西**！子模組之間請直接相互引用具體模組（例如 `from .base import BaseProvider`）。  
> 2. `__init__.py` 只能做**「單向門面匯出」**，不可作為子模組間的共用依賴中心！

> **白話比喻**：`__init__.py` 就是 Package 的**大樓前台接待櫃檯**，訪客不需要自己跑去 3 樓辦公室，在一樓櫃檯就能拿到所有公開的資料與工具！

### 4. `pyproject.toml` (專案中央指揮總部)

#### 名字由來
`pyproject` 即 **Python Project**；`.toml` 是 **Tom's Obvious, Minimal Language** 格式（比 JSON 更易讀、比 YAML 更不易出錯的現代設定檔格式）。

#### 它是什麼？在做什麼？
這是現代 Python 專案**最重要的唯一核心設定檔**（遵循 PEP 518 與 PEP 621 標準）。它把過去分散在 `setup.py`、`setup.cfg`、`requirements.txt`、`pytest.ini`、`.flake8` 的設定全部統合在一檔案中！

#### 主要三大區塊解密：
1. **`[build-system]` (建置系統)**：告訴 Python 該用什麼工廠工具（如 `setuptools` 或 `hatchling`）來把專案打包成 `.whl` 檔。
2. **`[project]` (專案元數據與依賴)**：記載專案名稱、版本號、作者資訊，以及專案運行所必須安裝的**第三方套件清單 (`dependencies`)**。
3. **`[tool.xxx]` (開發工具設定)**：統一設定各類開發工具的行為（如 `[tool.pytest.ini_options]` 或 `[tool.ruff]`）。

> **白話比喻**：`pyproject.toml` 就是專案的**中央指揮總部與身份證**，所有關於這個專案是誰、要用什麼工具、需要什麼零件的指令全部在這裡集中發佈

### 5. .env 與 .env.example

#### 名字由來
`env` 是 **Environment (環境變數)** 的縮寫。檔名開頭的點號（`.`）代表在 Unix / macOS 系統中這是一個**隱藏檔案**。

#### 它是什麼？在做什麼？
這是一對控制安全的**雙胞胎兄弟檔案**：

- **`.env` (私密實體鑰匙)**：存放真實的資料庫密碼、第三方 API Key、JWT 秘密金鑰。  
  👉 **此檔案必須絕對禁止進 Git（加入 `.gitignore`）！每個開發者電腦裡會有自己的一份。**
- **`.env.example` (公開範本說明書)**：存放範例結構與欄位名稱（不含任何真實密碼），例如 `DATABASE_URL=sqlite:///./test.db`。  
  👉 **此檔案會 Commit 入 Git 倉庫，供新進同仁複製並參考格式。**

> **白話比喻**：`.env` 是你家保險箱的**實體鑰匙**；而 `.env.example` 是鑰匙的**形狀草圖與複製說明書**

#### 🛠️ 實戰教學：在 Python 專案中該如何具體使用 `.env`？

在 Python 專案中使用 `.env` 的標準流程分為 **3 個步驟**：

##### 步驟 1：安裝 `python-dotenv` 套件
Python 原生並不會自動讀取 `.env` 檔案，需要透過社群最流行的 `python-dotenv` 套件來幫忙解析。使用現代 `uv` 工具安裝：
```shell
# 現代 uv 方式：極速安裝並自動將依賴寫入 pyproject.toml
uv add python-dotenv

# 或傳統相容方式
uv pip install python-dotenv
```


##### 步驟 2：編寫 `.env` 檔案（鍵值對格式 Key=Value）
在專案根目錄下建立 `.env` 檔案（不要寫 quotes 引號，變數名習慣全大寫）：
```env
# .env 本地私密金鑰檔案
APP_ENV=development
DEBUG=True
PORT=8000
DATABASE_URL=sqlite:///./dev.db
API_KEY=sk-proj-123456789abcdef
```

##### 步驟 3：在 Python 程式碼中載入並讀取變數
通常會在專案的 `config.py` 或程式進入點的第一行調用 `load_dotenv()`：

```python
# src/my_project/config.py

import os
from dotenv import load_dotenv

# 1. 核心動作：搜尋並載入當前目錄或上層目錄下的 .env 檔案
# load_dotenv() 會將 .env 中的變數注入到作業系統的環境變數 (os.environ) 中
load_dotenv()

# 2. 使用 os.getenv("變數名", "預設值") 取出變數
APP_ENV: str = os.getenv("APP_ENV", "development")
DEBUG: bool = os.getenv("DEBUG", "False").lower() == "true"
PORT: int = int(os.getenv("PORT", "8000"))
API_KEY: str | None = os.getenv("API_KEY")

# 3. 安全防護檢查：若必要的 API Key 未設定，立刻在中斷前發出警報
if not API_KEY:
    raise ValueError("致命錯誤：未在 .env 中設定 API_KEY，系統拒絕啟動！")

print(f"✅ 設定載入成功！當前環境: {APP_ENV}, 連線埠: {PORT}")
```

> **💡 行業進階技巧：`pydantic-settings`**  
> 在中大型企業專案中，開發者常結合 `pydantic-settings` 套件。它能自動將 `.env` 中的文字轉換為強型別 (int/bool/str)，並在欄位缺失時在編譯階段直接跳出提示，避免手動撰寫 `os.getenv` 與型別轉換！

`git` + `ignore` (忽略)。

> **白話比喻**：`.gitignore` 就是海關大樓的**禁運品清單與垃圾過濾網**，防止任何垃圾與危險物品被誤帶上飛機

### Step 2：建立與管理[[終端指令#虛擬環境|虛擬環境]] (使用現代極速 `uv`)

> **💡 為什麼選擇 uv 代替傳統 pip / venv？**  
> - **傳統 pip / venv 的痛點**：舊式 `python3 -m venv` 建置較慢，且預放的 `pip` 通常過舊，每次都需要手動 `pip install --upgrade pip`；此外 `pip install` 只會改動 `.venv` 資料夾，不會記錄在專案設定檔中。  
> - **現代 uv 的極致優勢**：`uv` 採用 Rust 開發，速度快 10~100 倍。使用 `uv venv` 能秒速建置包廂；後續配合 `uv add` 還能自動將套件名稱同步寫入 `pyproject.toml` 中，告別手動維護的麻煩！

### Step 6：撰寫生產級程式碼與測試範例

#### 1. 撰寫核心邏輯 (`src/my_project/core/calculator.py`)：

```python
# src/my_project/core/calculator.py

class ValueErrorException(Exception):
    """當輸入數值無效時拋出的自訂異常"""
    pass

def safe_divide(numerator: float, denominator: float) -> float:
    """安全除法計算

    Args:
        numerator (float): 分子
        denominator (float): 分母

    Raises:
        ValueErrorException: 當分母為 0 時拋出異常

    Returns:
        float: 除法運算結果
    """
    if denominator == 0:
        raise ValueErrorException("分母不可為零！")
    return numerator / denominator
```

#### 2. 在 `src/my_project/__init__.py` 導出對外 API：

```python
# src/my_project/__init__.py

__version__ = "0.1.0"

from .core.calculator import safe_divide, ValueErrorException

__all__ = ["__version__", "safe_divide", "ValueErrorException"]
```

#### 3. 撰寫 CLI 主入口 (`src/my_project/__main__.py`)：

```python
# src/my_project/__main__.py

from my_project import __version__, safe_divide

def main() -> None:
    print(f"=== 歡迎使用 My Project (v{__version__}) ===")
    res = safe_divide(10.0, 2.0)
    print(f"計算結果 (10 / 2) = {res}")

if __name__ == "__main__":
    main()
```

#### 4. 撰寫單元測試 (`tests/test_calculator.py`)：

```python
# tests/test_calculator.py

import pytest
from my_project import safe_divide, ValueErrorException

def test_safe_divide_success():
    """測試正常除法運算"""
    assert safe_divide(10.0, 2.0) == 5.0

def test_safe_divide_by_zero():
    """測試除以零時是否正確拋出自訂 Exception"""
    with pytest.raises(ValueErrorException):
        safe_divide(10.0, 0.0)
```
